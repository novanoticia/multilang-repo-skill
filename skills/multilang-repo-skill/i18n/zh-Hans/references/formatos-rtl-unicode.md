# 格式、RTL 与 Unicode（D16、D30、D31）

如果项目要格式化日期、数字、货币或对文本排序（[programa]），请阅读本文；有 [rtl-escrituras] 时则必须阅读。当某项标准对决定起关键作用时，请查阅其原始来源（R10）：BCP 47（RFC 5646 和 RFC 4647）、CLDR、UAX #9（双向性）、UAX #15（规范化）和 UTS #39（Unicode 安全机制）。

## 内容
- D16 依赖区域设置的格式
- D30 从右到左的文本与复杂文字
- D31 Unicode 策略：标记，而不是删除

## D16 依赖区域设置的格式

- 日期、时间、数字、货币、单位、排序和大小写转换，使用生态系统的机制（`Intl`、ICU、Babel、`java.text` 等）和所选的区域设置。不要自行重新实现。
- 默认语言**严格**保留其当前格式（D1）。如果改用生态系统的格式化器会改变其字节，则对默认语言继续使用当前格式，或申请例外。基线会检测到这一点。
- 对机器契约（键、命令、标识符）的操作不依赖区域设置。在 Java 中，默认区域设置为土耳其语时，`"i".toUpperCase()` 得到 `İ`，在 JavaScript 中 `toLocaleUpperCase("tr")` 同样如此：对这些契约使用不变的操作（`toUpperCase(Locale.ROOT)`，JavaScript 中用 `toUpperCase()`）进行比较和转换。
- 字符串在翻译后会变长。预留空间，不要悄悄截断，并用伪区域设置进行测试（P4）。

## D30 从右到左的文本与复杂文字

- 在载体上声明方向：HTML 中用 `dir="rtl"` 和 `lang`，CSS 中用逻辑属性（用 `margin-inline-start` 而不是 `margin-left`）。镜像具有方向性的图标。
- 用 `<bdi>`、用 U+2068…U+2069 隔离符，或用框架已有的隔离机制，隔离被插值的反向值（名称、路径、命令、数字）。这样，以拉丁字符书写的契约就不会在阿拉伯语或希伯来语的句子中被打乱顺序。
- 检查真实的显示效果：阿拉伯语的字母连写、印度系文字的合字、RTL 中的表格和 Markdown。许多终端不应用双向算法：对控制台工具，要么测试，要么声明该局限。
- 以显示测试（截图或经审阅的渲染输出）收尾，或声明该局限。如果审查者不读该语言，要如实说明。

## D31 Unicode 策略：标记，而不是删除

许多不可见字符是合法且必要的。不加区分地删除它们会破坏真实的语言：

| 字符 | 合法用途 |
|---|---|
| ZWNJ U+200C | 波斯语及其他语言的正字法（`می‌خواهم`） |
| ZWJ U+200D | 印度系文字的合字；emoji 序列（👨‍👩‍👧） |
| LRM/RLM U+200E/U+200F、ALM U+061C、隔离符 U+2066–U+2069 | 格式正确的双向文本 |
| 变体选择符 U+FE00–U+FE0F、U+E0100–U+E01EF | emoji 的呈现方式；表意文字的变体 |
| U+200B | 无空格语言（泰语、高棉语、老挝语、缅甸语）的换行 |
| U+00AD | 可选的音节断字 |
| U+1F3F4 之后的标签 U+E0020–U+E007F | 子区域旗帜（例如苏格兰旗） |

以下情形值得审查，因此要标记：
- 双向嵌入和覆盖 U+202A–U+202E。它们可能显示出与逻辑顺序不同的视觉顺序，并向审阅者隐藏真实内容（“Trojan Source”攻击的途径）。在 RTL 文本中，隔离符通常就够了。
- 值内部没有配对的双向控制符。
- 不在旗帜中的标签字符 U+E0000–U+E007F：不可见，可能隐藏文本。
- **机器契约**（键、占位符、命令、选项、URL）内的任何不可见字符、控制字符或文字混用：在那里它是错误，因为同形字或不可见字符会改变契约的身份。

流程：用 [scripts/validar_catalogos.py](../../../scripts/validar_catalogos.py) 生成报告，结合上下文审查每个案例，与用户一起决定，并只修正具体的那个案例。该脚本从不修改文件。没有发现的报告意味着没有找到这些模式，而不意味着文本是安全的（S6）。
