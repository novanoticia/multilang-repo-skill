# 计划、基线、测试、审查与分级处置（P1–P15）

在阶段 4 和阶段 8 阅读本文。按已批准的规模应用（SKILL.md 中 R20 的表），并将每项检查连同其级别（R7）记录在 [assets/evidencias-y-cierre.md](../assets/evidencias-y-cierre.md)。

## 内容
- P1–P3 计划、基线与提取
- P4–P8 测试与验证
- P9–P12 包、CI 与节奏
- P13 按场景评测指令

## 计划、基线与提取

**P1 计划。** 拆成小任务，每个任务带有自己的测试、文件和“完成”标准。如果实际范围比预期大，先说明再继续。在引导模式下，计划须在实施前获得批准，每个任务以其摘要收尾；在自主模式下，计划予以记录，并作为可更正的假设呈现（R18）。

**P2 基线，在动任何东西之前。** 从基础 commit 生成（`git show <base>:<ruta>`），不要从工作副本生成，并使其具有确定性：固定日期和路径、受控环境，二进制文件或 zip 按内容比较。
- 程序：在有代表性的模式和错误路径下，各语言的默认输出。
- 指令：用已批准替换的封闭清单运行 `verificar_adiciones.py`（若全是新增内容则清单为空）。由版本脚本机械处理的版本行，用一个模式批准。
- 清单文件：除版本外完全相同。
- 仅用 `git diff --numstat` 不够。它只统计行数，不说明哪些行变了：改了一行未批准的行而不是已批准的行，得到的数字相同。

**P3 用工具提取。** 按此顺序：生态系统自带的提取器；读取真实字面量的脚本（当数量值得时用 AST 或 codemod）；以及在规模 S 下手工提取，并检查每个字面量在原文中确实原样存在。提取器在零匹配和多匹配时都会失败，并能应对重复的句子、跨多行的句子、引文和缩进块。覆盖范围：所有可见文本要么是带键的字面量，要么是已声明的指令；被排除的内容连同理由一并列出。

## 测试与验证

**P4 伪区域设置。** 当文本通过代码进入界面或控制台时应用；如果没有价值（字符串很少且全都已列入清单），则连同理由省略。生成一种合成语言：每个句子都包在可见标记中，带重音符号，并加长 30%。输出中没有标记的是目录之外的字面量；被截断的是空间问题。这是一次 `local`（本地）执行，不是模拟。不对外分发，也不适用于模型生成的文本。

**P5 在有证据价值之处先写测试。**
- 带新行为的代码（选择、回退、格式、脚本、验证器）：先写测试，看它失败，再实现。
- 不变性测试（默认输出不变、契约不变）：按设计从一开始就通过。它们的价值通过故意破坏其所保护的内容来证明（P7），而不是通过看到它们变红。
- 内容（目录）：由验证器充当测试。
- 文档：不做 TDD。

不要为了形式而编造先红的测试。

**P6 目录验证。** 优先使用生态系统的验证器。对于没有验证器的自有 JSON 目录或 i18next 目录（非 ICU 也非 ARB），使用 [scripts/validar_catalogos.py](../../../scripts/validar_catalogos.py)：

```bash
python3 <skill>/scripts/validar_catalogos.py ruta/catalogos --referencia es \
  [--marcadores llave|doble-llave|printf] [--plurales sufijo] [--idiomas es,en,fr]
```

基本检查：键相同；没有空值，也没有 `TODO`；带名称的占位符在各语言间一致；反引号之间的内容一致；列表的条目数相同；仅当声明为不变时才允许与参照文本相同；状态与审阅者一致（D12）；形式（D13）；以及 Unicode（D31）。再加上项目自己的规则：术语表、数据格式，以及带有未翻译原文词语的高风险短语（作为启发式，而非定论；P8）。如果验证器拒绝你的内容，修正内容，而不是验证器。

**P7 对你编写的检查做破坏测试。** 新检查只有在亲眼看到它对应该检出的破坏失败后才算数。故意破坏一份副本，每次只破坏一处：
- 守卫：如果未破坏的套件在同一环境中不能通过，就不要测量任何东西。
- 每次破坏只应用一次。如果找不到目标或找到多处，那是工具的失败，不是成功。
- 记录每次破坏由哪项检查检出。如果只有通用测试（路径、环境）检出它，则视为未检出。
- 幸存者要么用新测试关闭，要么论证其等价。在通过守卫之前，绝不引用“100%”或“N 中的 N”。
- 在规模 L 下，如果有独立审查者，也用并非你设计的破坏（审查者的破坏）进行测量。
- 典型失败：接受别处重复出现的句子的断言、恰好巧合的数字、同义反复的测试、在错误层级读取的 YAML、掩盖变化的规范化。固定字面字符串的测试是快照，不是行为测试：要如实说明。
- 不要对生态系统的标准工具或本 skill 的脚本做破坏测试：它们已有自己的测试。针对项目调整过的副本（D7）则是你自己的代码。

**P8 相近语言之间的启发式。** 基于共有词语的启发式在相近语言（西班牙语、加利西亚语、葡萄牙语、加泰罗尼亚语）之间可能毫无用处。如果是这样，就显式省略它（跳过测试并写明理由），并用正字法标记或逐词审阅取代。忽略反引号之间的内容。

## 包、CI 与节奏

**P9 [paquete] 包测试。** 在没有 `.git` 和旧产物的临时副本中，运行真实的打包，并将清单与预期比较：既不能少一个文件（脚本没有复制的新子文件夹），也不能多一个文件（测试、会话记录、模板副本、工具）。展示清单（`unzip -l` 或等效命令）。

**P10 CI。** 使用现有的 CI。只有在用户需要时才提议一个最小的：只读权限，仅当测试与 git 比较时才取完整历史，以及你所在规模的验证器和测试。从未运行过的 workflow 不是证据。检查项的名称是 job 的 `id` 或其 `name`，并须在真实运行中确认。用平台的工具读取结果，不要使用轮询循环。没有推送权限就没有运行：级别保持为 `local`（本地），CI 为 `pendiente`（待办）。关于 CI 状态的断言无法从仓库中监视：给它注明日期和引用（R8）。如果用户要求“CI 变绿”而没有 CI 或远程仓库，要在消息中说明，而不只是写在记录里：没有可以变绿的 CI，也无法从这里核实。没有 CI 时，状态为 `no aplica`（不适用）并写明该理由；如果用户接受最小 workflow，则保持 `pendiente`，直到它在平台上运行。套件通过应报告为 `local`。

**P11 可维护的版本测试。** 如果测试固定了版本号，下一次版本变更会使 CI 变红。让它从清单文件读取版本。

**P12 每个任务之后。** 你所在规模的检查全部通过：套件、验证器、基线，以及（如果你改动了检查）它们的破坏测试。

## P13 按场景评测指令

用于只有模型才能展示的内容（响应语言、警告、失效安全、对数据中指令的抵抗）。模板：[assets/escenarios-evaluacion.md](../assets/escenarios-evaluacion.md)。
1. **预先登记**，在运行任何东西之前：输入、通过标准、失败标准，以及各一个示例。期望的文本来自目录。标准容忍合理的变化（填充的空位、数字），但又不能弱到任何输出都能通过。
2. **运行**每个场景，使用隔离的上下文（新的子智能体、另一个会话），包由真实脚本构建，场景消息放在 prompt 中。执行者不知道通过标准。评估者是另一个智能体或一个人。虚构案例，并标明为虚构。
3. **阅读**回答和备注，而不只是结论：会出现没有任何标准预料到的发现。询问执行者读了哪些文件、觉得什么含糊。
4. 如果在看到结果后修改了某项标准，将其记录为事后变更并写明理由。
5. 修正之后，仅对受影响的场景进行第二轮，使用新的执行者和同样的标准。
6. 声明局限：这是模拟，不是真实平台；所读文件的清单由执行者自己声明；每个场景运行一次无法衡量变异性；模型不等于人工审阅。留一张表用于真实运行（平台、模型、日期、结果）。
7. 如果没有隔离的上下文，或用户不授权委派（M1），场景保持预先登记并为 `pendiente`（待办）。不要在你自己的上下文中扮演它们并作为已执行呈现。

## 独立审查与分级处置

**P14 审查。** 独立是指由上下文干净、拥有只读访问权限、且不接收你的结论的审查者：在可用且获授权（M1）时是子智能体，否则是一个人。如果都没有，就做自我审查并如实声明。最低清单：字面花括号和带花括号的数据；开发环境的污染；形似区域设置的代码；各语言间一致的机器格式；不完整的目录；输出和产物中混杂的语言；自身检测器无法识别的建议（D19）；规则之间的冲突（D21）；被当作指令处理的方括号列表；语言的持久性；在会停止的路径中缺失的警告；对官方名称的意译；没有键的字面量；悄悄降级的输入；缺少新文件的安装途径；以及文档中不再吻合的数字。高风险时，对关键内容进行人工审阅。

**P15 分级处置。** 关键和重要的问题用一个先失败的测试来修正（或用证明该检查有效的破坏）。次要的问题连同理由记下，写入报告。会改变默认输出或与原文契约的内容，要记下，未经批准不要触碰。修正之后，对新检查重复破坏测试。
